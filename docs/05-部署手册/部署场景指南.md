## 1. 单机多进程（Unix Socket）

### 1.1 场景说明

单机多进程是最常见的部署形态：同一台主机上运行多个进程，进程间通过 SSN 通信。
典型场景包括：

- 服务拆分：网关进程与业务进程分离，各自独立部署、独立升级；
- 模块隔离：将高负载或高风险模块放入独立进程，形成崩溃域隔离；
- 多租户：同机多个应用共享一套 IPC 框架。

同机通信选用 Unix Socket（`unix://`）而非 TCP：Unix Socket 不经过网络协议栈，
延迟低、吞吐高，且天然不占用 TCP 端口，不存在端口冲突问题。

### 1.2 部署要点

1. **地址格式（前缀必需）**：Unix Socket 地址必须使用 `unix://` 前缀，
   形如 `unix:///tmp/app_a.sock`。服务端 `ssn_server_create` 传入的名字若不含
   `://` 会按 Unix Socket 路径处理（自动补前缀），但建议始终显式写全前缀，
   避免与其他协议混淆。
2. **路径规划**：socket 文件建议放在专用目录，如 `/tmp` 或
   `/var/run/<应用名>/`。注意路径长度限制（Unix Socket 地址长度有限），
   目录必须提前创建并保证写权限。
3. **socket 文件清理**：
   - 服务端 `ssn_server_start` 启动时自动删除残留的 socket 文件（仅当
     目标文件是 socket；若同名文件是普通文件则报错启动失败）；
   - 因此进程异常退出（如 `kill -9`）后残留的 socket 文件，下次启动会自动
     清理，无需人工干预；
   - 正常退出时由程序在 `ssn_server_destroy` 之后手动删除 socket 文件
     （参考 `examples/protocols/01_unix_socket` 示例）；
   - 不要用普通文件占用 socket 路径。
4. **权限控制**：socket 文件权限继承创建进程的 umask，同机多进程一般以同一
   用户运行即可互通；多用户场景需确保 socket 所在目录对通信双方都可读可写。
5. **事件循环必须驱动**：服务端进程必须调用 `ssn_server_poll` /
   `ssn_server_run` 驱动事件循环，连接与消息处理才得以进行（详见第 4 章）。

### 1.3 示例拓扑

```
┌────────────────── 主机 A（单机） ──────────────────┐
│                                                    │
│  ┌──────────────┐          ┌──────────────┐        │
│  │ 网关进程      │  unix:// │ 业务进程      │        │
│  │ ssn_server   │◄────────►│ ssn_client   │        │
│  │ unix:///tmp/ │   /tmp/  │ 连接网关地址   │        │
│  │ gateway.sock │ gateway. │              │        │
│  └──────────────┘   sock   └──────────────┘        │
│                                                    │
│  ┌──────────────┐          ┌──────────────┐        │
│  │ 数据库代理进程 │  unix:// │ 报表进程      │        │
│  │ ssn_server   │◄────────►│ ssn_client   │        │
│  │ unix:///tmp/ │   /tmp/  │              │        │
│  │ db_proxy.sock│ db_proxy.│              │        │
│  └──────────────┘   sock   └──────────────┘        │
└────────────────────────────────────────────────────┘
```

### 1.4 部署检查清单

- [ ] 所有地址均使用 `unix://` 前缀，路径在 `sockaddr_un` 长度限制内；
- [ ] socket 目录存在且通信双方进程对其有读写权限；
- [ ] socket 路径不与任何普通文件同名；
- [ ] 服务端进程有驱动 `ssn_server_poll` / `ssn_server_run` 的事件循环；
- [ ] 正常退出流程为：退出 poll 循环 → `ssn_server_destroy` → 删除 socket 文件；
- [ ] 异常退出后重启验证：启动日志确认旧 socket 文件已被自动清理。

## 2. 跨节点（TCP + 发现）

### 2.1 场景说明

跨节点部署将服务分布在多台主机上，进程间通过 TCP 通信。典型场景包括：

- 服务分离：前端机与后端机分离，后端服务按模块分布在不同主机；
- 横向扩展：同一种服务部署多份实例，客户端按需连接；
- 远程访问：客户端主机与服务器主机不在同一物理机。

跨机通信必须选用 TCP（`tcp://`），Unix Socket 仅在同一主机内可用。

### 2.2 部署要点

1. **地址格式（前缀必需）**：TCP 地址使用 `tcp://host:port` 格式，
   如 `tcp://192.168.1.10:8080`。服务端监听地址可为具体 IP 或 `0.0.0.0`
   （监听所有网卡）；客户端必须填写服务端实际可达的 IP 与端口。
2. **端口规划**：服务端端口需固定并全局唯一，避免与其他服务冲突；部署前
   确认端口未被占用（`sshd`、其他业务等），并对端口分配登记在案。
3. **节点发现配置**：
   - 当前版本（v2.5.6）**未实现自动节点发现**：代码中仅有能力位
     `SSN_NODE_CAP_DISCOVERY`，组播/目录服务发现属于设计文档中的规划能力
     （`docs/03-设计/核心模块/节点发现设计.md`，状态为部分过时）；
   - 因此跨节点互联必须**显式配置对端地址**：客户端通过
     `ssn_client_connect(addr, ...)` 连接固定地址；节点抽象通过
     `ssn_node_subscribe` 的 `peer_address` 参数（v2.1.0 起必填）指定对端；
   - 建议将服务端地址集中登记（配置文件、环境变量或配置中心），便于变更。
4. **防火墙与网络**：
   - 防火墙放行服务端监听端口；云环境注意安全组规则；
   - 多网卡绑定：`server_options_t.ifname` 选项已预留、当前版本未生效
     （代码仅存储该字段，未参与绑定），需通过监听地址本身控制，如
     `tcp://0.0.0.0:port`（监听所有网卡）或具体网卡 IP；
   - 服务端启用 TCP 保活（`SO_KEEPALIVE`：idle 默认 10 秒、间隔 10 秒、
     次数 3），用于尽早发现物理断链（详见第 4 章 idle/keepalive 说明）；
   - NAT / 跨网段环境确认双向路由可达，避免半开连接。

### 2.3 示例拓扑

```
┌──────────── 主机 A（服务端） ────────────┐
│  ┌──────────────────────────────┐       │
│  │ 订单服务 ssn_server          │       │
│  │ tcp://192.168.1.10:8080      │       │
│  └──────────────────────────────┘       │
│  ┌──────────────────────────────┐       │
│  │ 库存服务 ssn_server          │       │
│  │ tcp://192.168.1.10:8081      │       │
│  └──────────────────────────────┘       │
└─────────────────────────────────────────┘
        ▲                    ▲
        │ tcp://:8080        │ tcp://:8081
        │                    │
┌───────┴──────┐      ┌──────┴────────┐
│ 主机 B（网关）  │      │ 主机 C（报表）   │
│ ssn_client    │      │ ssn_client    │
└───────────────┘      └───────────────┘
```

### 2.4 部署检查清单

- [ ] 服务端与客户端地址均为 `tcp://host:port` 完整格式；
- [ ] 服务端监听 IP、端口已固定并登记，无端口冲突；
- [ ] 防火墙/安全组已放行服务端监听端口；
- [ ] 客户端连接的地址在目标网络可达（跨网段/NAT 已确认路由）；
- [ ] 对端地址已显式配置（无自动发现，勿依赖未实现能力）；
- [ ] 多网卡主机已通过监听地址（具体网卡 IP）控制绑定（`ifname` 选项
      当前版本未生效）。

## 3. 混合传输场景

### 3.1 场景说明

大型系统常采用混合部署：同主机内部组件用 Unix Socket 获得低延迟，跨主机
组件用 TCP 保证可达。典型形态：

- 主机内部：网关进程 ↔ 本地模块（`unix://`）；
- 主机之间：本地网关 ↔ 远端服务（`tcp://`）。

两种传输在同一应用中共存，由地址格式区分，对上层协议透明。

### 3.2 部署要点

1. **按位置选型**：同机通信一律用 `unix://`（延迟与吞吐优先），跨机通信
   用 `tcp://`；地址前缀必须写全，传输类型由地址前缀自动识别。
2. **客户端连接多地址**：
   - 一个 `ssn_client` 实例一次连接一个地址；需要同时连接多个服务时，为
     每个目标创建独立 client 实例（每个实例持有一条连接）；
   - 需要自动重连时使用 `ssn_client_auto`（可配置应用层 keepalive 心跳，
     间隔最小 50ms，用于保活与断线检测）；
   - 使用节点抽象时，`ssn_node_subscribe(peer_address, ...)` 的
     `peer_address` 为必填参数（v2.1.0 起），按对端地址建立连接；
   - 对端地址变更时更新配置即可，无需改动协议层代码。
3. **传输实例的线程归属**：传输层本身不是线程安全的，同一传输实例不应被
   多线程同时访问；多线程场景每个线程使用独立实例，或外部加锁保护
   （详见 `docs/03-设计/架构设计/传输层设计.md`「线程安全性」）。
4. **运维视角一致**：idle/keepalive 行为、事件循环驱动、优雅退出顺序对
   两种传输一致（见第 4 章），混合部署时同一套运维规范适用。

### 3.3 示例拓扑

```
┌──────────────── 主机 A ─────────────────┐
│                                        │
│  ┌──────────────┐   unix://   ┌───────┐│
│  │ 交易处理进程   │◄───────────►│ 风控模块││
│  │ ssn_server   │  /tmp/trade │ (client)│
│  └──────┬───────┘    .sock    └───────┘│
│         │ tcp://192.168.1.10:9090      │
└─────────┼──────────────────────────────┘
          │ tcp://
          ▼
┌──────────────── 主机 B ─────────────────┐
│  ┌──────────────────────────────┐      │
│  │ 清算服务 ssn_server          │      │
│  │ tcp://192.168.1.20:9090      │      │
│  └──────────────────────────────┘      │
└────────────────────────────────────────┘

同一进程内可同时持有：
  - unix:// 连接（同机模块，如 交易→风控）
  - tcp://  连接（跨机服务，如 交易→清算）
```

### 3.4 部署检查清单

- [ ] 同机组件地址为 `unix://`，跨机组件地址为 `tcp://`，前缀均写全；
- [ ] 一个客户端实例只连接一个地址，多对端使用多个实例（或节点抽象多订阅）；
- [ ] 需要自动重连的客户端已改用 `ssn_client_auto` 并配置 keepalive；
- [ ] 同一传输实例未跨线程共享（或已外部加锁）；
- [ ] 混合部署沿用统一的 idle、事件循环与退出规范（见第 4 章）。

## 4. 服务端运维场景

### 4.1 场景说明

服务端进程长期运行，运维关注：事件循环是否被正确驱动、长连接的空闲处理
（idle/keepalive）、以及停服时的优雅退出顺序。本节给出与代码行为一致的
运维基线（对应 v2.4.0）。

### 4.2 事件循环驱动（server poll 线程模式）

- SSN 服务端**不自动运行 poll 线程**，事件循环必须由应用驱动：
  - `ssn_server_poll(server, timeout_ms)`：单次轮询，基于 `pselect` 实现，
    可被信号中断，适合嵌入应用主循环或独立线程中周期调用；
  - `ssn_server_run(server)`：阻塞式无限循环，直到进程退出；
  - 客户端同理：`ssn_client_poll` / `ssn_client_run`。
- 服务端存在一个**全局定时器线程**（50ms 周期），它只负责 idle/握手超时的
  计时并在到期时通过 eventfd 唤醒 poll 循环；连接建立、消息收发、超时断开
  的实际处理仍在应用的 poll 循环中完成。因此：
  - 应用必须保持 poll 循环活跃，长时间不调用 poll 会导致连接无法处理、
    idle 超时无法生效；
  - poll 被信号中断时会自动重试（`EINTR` 处理），无需应用处理。
- 独立 poll 线程模式示例：

```c
// poll 线程：循环驱动服务端事件
void *server_poll_thread(void *arg)
{
    ssn_server_t *server = (ssn_server_t *)arg;
    while (g_running) {
        ssn_server_poll(server, 100);   // 100ms 周期轮询
    }
    return NULL;
}
```

### 4.3 idle / keepalive 行为说明

服务端对每条已握手连接进行应用层 idle 计时，行为如下（v2.4.0）：

- **默认值**：应用层 idle 默认 **10 秒**（`IPC_SERVER_KEEPALIVE_TIMEOUT`，
  使用 `ssn_server_create` 不传选项时生效）；可通过
  `server_options_t.idle_timeout_sec` 覆盖，设为 `<= 0` 可禁用 idle 断开；
- **活跃连接自动重置**：握手完成后，连接每次收到数据包都会**自动重置
  idle 计时**——只要客户端持续收发，连接不会被 idle 机制断开；
- **断开流程**：连接空闲超过 idle 阈值后，定时器线程标记该连接并通过
  eventfd 唤醒 poll 循环，由 poll 循环直接断开并销毁该连接——此路径
  不触发连接断开回调（回调仅在连接对端关闭（EOF）或收包出错时触发）；
- **TCP 层保活（SO_KEEPALIVE）**：服务端创建传输时启用 TCP 保活
  （idle 取 idle 超时值、间隔 10 秒、次数 3），用于检测物理断链
  （网线拔除、对端宕机等），与应用层 idle 相互补充；
- **客户端侧心跳**：使用 `ssn_client_auto` 可配置应用层 ping 心跳
  （keepalive 参数，间隔毫秒，最小 50ms），适合需要主动保活的场景。

运维提示：连接数较多时，将 idle 设为较长值（如 60 秒）可减少无效连接的
频繁建立；对时延敏感场景保持默认 10 秒即可快速回收僵死连接。

### 4.4 优雅退出（stop/destroy 顺序）

停服必须按顺序执行，避免资源泄漏与崩溃：

1. **服务端**：SSN 服务端无单独的 stop API，正确顺序为——
   - 置退出标志，退出 poll 循环（`ssn_server_poll` 返回后 break，
     `ssn_server_run` 需通过标志自行跳出或由进程退出中断）；
   - 调用 `ssn_server_destroy(server)`：关闭监听与全部客户端连接，释放
     协议层与传输层资源（注意与 `ssn_server_create` 调用互斥）。
2. **客户端**：先 `ssn_client_disconnect(client)` 断开连接，再
   `ssn_client_close(client)` 销毁实例。
3. **节点抽象**：先 `ssn_node_stop(node)` 停止，再 `ssn_node_destroy(node)`
   销毁（顺序不可颠倒）。
4. **回调约束**：连接/消息回调可能在其他线程执行，回调中不得直接调用
   `ssn_server_destroy` / `ssn_client_close`（参见
   `docs/03-设计/核心模块/线程安全设计.md`），应置退出标志、由主流程退出后
   统一销毁。

### 4.5 部署检查清单

- [ ] 服务端进程存在活跃的 poll 循环（主循环或独立 poll 线程），未长期空转；
- [ ] idle 超时按业务设置（默认 10 秒，需变更时通过
      `server_options_t.idle_timeout_sec` 配置，≤0 禁用）；
- [ ] 已确认"活跃连接收包自动重置 idle 计时"的行为，避免误判超时；
- [ ] TCP 传输已启用保活（服务端默认开启），物理断链可被检测；
- [ ] 停服顺序：退出 poll 循环 → `ssn_server_destroy`；客户端
      disconnect → close；节点 stop → destroy；
- [ ] 回调中未直接调用销毁接口，销毁统一在主流程进行；
- [ ] 重启验证：旧 socket 文件自动清理（Unix），端口可重新绑定（TCP，
      已启用地址复用）。
