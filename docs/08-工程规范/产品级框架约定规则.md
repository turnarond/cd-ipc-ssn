## 2. 产品治理与战略

**原则：任何变更若无法在战略文档中找到对应条目，视为非法需求蔓延。**

### 2.1 产品定位

SSN（Scalable Socket Network，可扩展套接字网络）是一个轻量级 IPC/分布式通信框架——完整 IPC 栈（框架而非某层协议），支持 RPC、发布/订阅、点对点消息，运行于 Unix Domain Socket / TCP / UDP 之上。命名定义统一措辞，位于 `README.md` 首段、`docs/01-白皮书/架构白皮书.md` 1.1、`docs/02-需求分析/需求分析.md` 1.1。

### 2.2 白皮书

- 位置：`docs/01-白皮书/架构白皮书.md`；
- 内容：愿景、价值主张、适用场景、业务边界（明确写绝不做哪些事）、总体架构；
- 维护：每次**主版本号（Major）**发布，必须同步修订白皮书。

### 2.3 路线图

- 位置：`docs/03-设计/DDS演进设计.md`（当前路线：DDS 三阶段 2.5.0/2.6.0）、版本规划见 `docs/superpowers/specs/` 与发布计划；

## 3. 版本与发布契约

### 3.1 语义化版本（SemVer）

严格遵循 `主版本号.次版本号.补丁号`：

| 版本 | 触发条件 |
|------|----------|
| 主版本（Major） | 不兼容的 API/架构变更 |
| 次版本（Minor） | 向下兼容的功能新增 |
| 补丁（Patch） | 向下兼容的纯 Bug 修复 |

### 3.2 发版同步清单（四项缺一不可）

1. `VERSION` 文件；
2. `src/version/ssn_version.h` 的 `SSN_VERSION_*` 宏与 `SSN_VERSION_STRING`；
3. `CMakeLists.txt` 的 `VERSION_MAJOR/MINOR/PATCH` 与 `SOVERSION`；
4. `CHANGELOG.md`（按 Added / Changed / Fixed / Removed 分组记录，格式参照现有条目）。

发版提交后打 Git Tag：`git tag vX.Y.Z`，并推送 tag。

### 3.3 需求冻结与范围治理

- **冻结期**：版本发布前 3 个工作日进入「静默期」，仅接受 P0 级紧急修复；
- **防蔓延铁律**：任何非当前版本需求列表中的新想法、UI 微调、重构意图，严禁以「顺便做一下」的理由塞入当前迭代；
- **操作标准**：新需求必须创建 Issue，标记 `Next-Version`，在下一个版本规划中排期。

## 4. 工程标准

### 4.1 命名规范

- 公开符号统一 `ssn_` 前缀；VSI 平台抽象内部保留 `ipc_` 前缀（仅内部使用）；
- 类型：`ssn_<module>_t`；函数：`ssn_<module>_<action>`；宏：`SSN_UPPER_CASE`；
- 变量与函数 snake_case；结构体用 `typedef struct` 定义并加 `_t` 后缀，成员按类型大小排序（大的在前）。

### 4.2 代码风格

- 缩进：4 空格，不使用制表符；`{` 放在行尾、`}` 放在新行；控制语句（if/for/while/switch）必须使用大括号；
- 注释：文件头注释说明文件功能；函数注释说明功能/参数/返回值；行内注释用 `//`（与代码至少一个空格）；长注释用 `/* */`；注释说明「为什么」而非「是什么」；
- 头文件：包含顺序为系统头文件 → 第三方头文件 → 自定义头文件；必须使用 `#ifndef`/`#define`/`#endif` 保护；
- 错误处理：错误必须用 `LOG_ERROR`/`LOG_WARNING` 等日志记录；错误码统一使用 `ssn_error.h` 中的 `SSN_ECODE_*`；返回值明确表示成功/失败；
- 长度限制：函数 ≤ 200 行；每行 ≤ 120 字符；
- 工具：clang-format（`.clang-format`）统一格式化；cppcheck 静态分析；定期代码审查。

### 4.3 架构分层铁律（依赖方向由外向内）

| 层 | 职责 | 位置 |
|---|---|---|
| 节点抽象层 | server + client 双角色封装 | `src/node/ssn_node.c` |
| 客户端/服务端层 | 连接管理、事件循环、消息路由、引用计数线程安全 | `src/ssn_client.c`、`src/ssn_server.c`、`src/ssn_cliauto.c` |
| 协议层 | RPC 请求/应答、发布/订阅、点对点消息 | `src/protocol/{rpc,pubsub,msg}/` |
| 线协议 | 帧编解码 | `src/ssn_frame.c` |
| 传输层 | Unix/TCP/UDP + 工厂；地址格式 `tcp://host:port`、`unix:///path`、`udp://host:port` | `src/transports/` |
| VSI 平台抽象 | 套接字/事件/线程/互斥锁，仅内部使用（保留 `ipc_` 前缀） | `src/vsi/` |

- 数据流（发送）：Node → Client → Protocol → Transport；接收方向相反；
- **新增代码必须符合既有分层边界，不得越层调用**；
- Clean Code：函数短小单一职责（≤ 200 行）、命名表达意图、消除重复（DRY）、无死代码、错误处理完整；
- Clean Architecture：接口依赖倒置、模块间通过接口解耦、可独立测试。

## 5. 开发流程 SOP

### 5.1 TDD 铁律

- 循环：严格遵循**红-绿-重构**——先写/更新测试 → 确认测试因正确原因失败（红）→ 实现最小修复（绿）→ 重构改进（保持绿）；
- **禁止**：没有失败测试的情况下编写任何生产代码；每次实现必须附带对应测试代码，或指明要让它变绿的测试用例；
- 新需求先在 `test/` 中编写对应测试用例；bug 修复先编写能复现问题的回归测试；
- 测试在本机 WSL 中运行（仓库位于 Windows，Linux 构建环境在 WSL）：

```bash
wsl bash -c "cd /mnt/d/personal/cd-ipc-ssn && bash test/run_tests.sh"
```

### 5.2 标准作业程序（八步）

| 步骤 | 动作 | 产出/检查点 |
|------|------|------------|
| Step 0 | 战略对齐 | 确认需求在路线图/需求清单中有对应版本归属 |
| Step 1 | 分支创建 | `git checkout -b feature/xxx`（或 fix/xxx、issue/编号） |
| Step 2 | 文档先行 | 更新 `docs/03-设计/` 下的 API 设计或架构图 |
| Step 3 | 测试先行（红） | 编写测试，确认测试因正确原因失败（Red） |
| Step 4 | 编码实现（绿） | 编写最少代码使测试变绿（Green），严格遵守分层铁律 |
| Step 5 | 重构 | 优化代码坏味道，确保测试始终保持绿色 |
| Step 6 | 文档同步 | 更新 `CHANGELOG.md` 和 API 文档/使用手册 |
| Step 7 | 提交合并 | 发起 PR，包含代码、测试、文档变更；提交信息格式：`type(scope): 中文描述`（如 `fix(server): ...`、`docs: ...`），TDD 相关提交附 `[TDD]` 标识 |
| Step 8 | 版本标签 | 发布时打 Git Tag，严格遵守 SemVer |

### 5.3 分支策略

- 需求变更：`feature/<简述>`（如 `feature/node-discovery`）；
- Bug 修复 / issue 修改：`fix/<简述>`（如 `fix/client-deadlock`）或 `issue/<编号>`；
- **禁止**：直接在 `main` 上提交；开发完成、测试通过后合回 `main`。

## 8. 工具与协作

### 8.1 工具化思维

- 遇事必造：复杂数据模拟、环境检查、冒烟测试、压力验证等需求，优先创建工程工具集；
- 存放位置：`test/`、`examples/utils/` 或 `tools/`（按性质）；
- 工具脚本保持 LF 行尾（.gitattributes 已强制）、位置无关（基于脚本自身路径定位仓库根）；
- 工具本身配有 README 与测试用例，确保稳定可靠。

### 8.2 问题追踪

- 延迟处理：开发过程中发现的非阻断性问题，若时间不足，**禁止私自修改代码**；
- 记录债务：必须创建对应 Issue（GitHub Issues），打上「技术债」标签，关联到未来版本路线图，在适当时机集中修复；
- 已记录的问题（含位置与严重性）应可在 `.remember/` 或 issue 列表中追溯。

### 8.3 代码审查

- 作者与评审分离：authoring 与 review 必须是独立的两次 pass，禁止在同一上下文自审自批；
- 审查范围：规格符合性 + 代码质量（Clean Code/Architecture、测试充分性、文档同步）；
- 审查发现按严重级（Critical/Important/Minor）分级处理；Critical/Important 必须修复后才可合并。

### 8.4 环境约定

| 项 | 约定 |

## 9. 生产级韧性（目标态声明）

**原则：如实标注现状，不把目标态写成事实。** 全局规范要求以下韧性能力，SSN 作为嵌入式 C 库逐条裁定：

| 全局要求 | SSN 现状 | 裁定 |
|----------|----------|------|
| 结构化日志（JSON + trace_id/user_id/duration） | `LOG_*` 宏体系（`src/util/`），非 JSON | **不适用**：库级日志格式由宿主应用决策，保持日志宏体系规范即可 |
| 业务指标代码埋点 | `ssn_node_get_stats`（连接数/消息计数） | **已具备**：基础计数由代码产出，扩展指标随功能新增 |
| 写操作幂等（Idempotent-Key） | RPC 请求/应答无事务语义；协议层无去重键 | **部分适用**：协议无「写操作」概念；应用层按需实现去重 |
| 熔断 / 超时重试 / 优雅降级 | `ssn_cliauto` 自动重连 + 超时参数；无熔断、无退避重试 | **待落地**：客户端重试退避策略列入后续版本规划 |
| 声明式部署（Dockerfile/compose） | 库产品，非服务 | **不适用**：可提供容器集成示例（可选） |
| 一键回滚 | Git Tag 回滚（`git tag vX.Y.Z` + 分支） | **已具备**：git 层面天然支持 |
| DB 迁移向前兼容 | 无数据库 | **不适用** |
| 优雅停机 | `ssn_node_stop/destroy` 顺序约定；服务端 stop 等待事件循环退出 | **已具备**：见部署手册与使用指南 |

## 10. 强制检查清单（Pre-Merge / Pre-Release）

在合并 PR 或发布版本前，必须通过以下检查项，**一项未通过则阻塞**：

- [ ] **版本关联**：代码变更对应路线图/需求清单中的某项；未违反范围冻结期；
- [ ] **TDD 绿线**：WSL 全量回归——14 自动化套件 + 19 示例构建全绿；
- [ ] **覆盖率**：核心 ≥ 90%、整体 ≥ 80%（当前以用例覆盖 + 回归登记为度）；
- [ ] **文档同步**：`docs/03-设计`、`docs/06-使用手册`、`CHANGELOG.md` 随代码更新；`docs/README.md` 链接完整；
- [ ] **幂等检查**：新增写接口保证幂等性（如适用）；
- [ ] **兼容性**：Major 升级已迁移白皮书与迁移指南；API 变更已标注 Deprecated；
- [ ] **分支规范**：变更在 `feature/*`、`fix/*` 或 `issue/*` 分支上，未直接提交 main；
- [ ] **环境规范**：CRLF/LF 无污染（sed 后已恢复）；.sh 脚本 LF 且位置无关；
- [ ] **命名一致性**：公开面无旧 `ipc_` 命名泄漏（VSI 内部除外）。
