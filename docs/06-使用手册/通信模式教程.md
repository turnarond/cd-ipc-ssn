# SSN 通信模式教程

> 适用范围：需要选择通信模式的 SSN 使用者。前置阅读：[使用指南](./使用指南.md)（构建、基础概念）；API 细节见 [API使用指南](./API使用指南.md)。本文所有代码示例均基于真实 API（对照 `src/ssn_client.h`、`src/ssn_server.h`、`src/node/ssn_node.h`），完整可运行版本见 `examples/basic/` 与 `examples/node/`。

## 1. 通信模式总览

SSN 支持四类经典通信模式，分别对应不同的通信语义（是否同步等待应答、是点对点还是一对多）：

| 模式 | 典型场景 | SSN 对应 API | 参考示例 |
|---|---|---|---|
| REQ/REP（请求应答） | 远程调用、查询/计算服务、配置读写（同步请求 + 应答） | `ssn_client_call` + `ssn_server_add_method` | `examples/basic/02_rpc_call` |
| PUB/SUB（发布订阅） | 事件通知、状态广播、新闻推送（异步、一对多、无应答） | `ssn_server_publish` + `ssn_client_subscribe` | `examples/basic/03_pubsub` |
| PUSH/PULL（管道） | 任务分发、负载均衡、流水线（点对点单向；SSN 无内置队列，需应用层管理） | `ssn_client_message` + `ssn_server_message` | `examples/basic/01_hello_world` |
| PAIR（对等） | 两个进程之间双向对等通信（一对一） | `ssn_node_send_to_peer` / `ssn_node_rpc_call` | `examples/node/02_node_comm`、`examples/node/03_node_rpc` |

选型速览：

- 需要应答 → REQ/REP（或 PAIR 中的节点 RPC 调用）；
- 一对多广播、不需要应答 → PUB/SUB；
- 一对一无应答、单向推送 → PUSH/PULL（队列与应用层自行管理）；
- 两个进程彼此对等、既发又收 → PAIR。

四类模式的详细教学见第 2～5 章，每章按「何时用 / 怎么用（代码）/ 常见坑」组织；综合决策流程见第 6 章。

## 2. REQ/REP（请求应答）

### 2.1 何时用

- 需要「一问一答」语义的场景：远程函数调用、查询/计算服务、配置读写、健康检查；
- 调用方关心结果（成功/失败、返回值），且可以接受等待应答；
- 典型形态是客户端/服务端架构：服务端注册方法，客户端发起调用。

REQ/REP 是同步语义的异步实现：`ssn_client_call` 本身立即返回（异步发送），应答通过回调返回，由调用方的事件循环（`ssn_client_poll` / `ssn_client_run`）驱动；超时由 `timeout_ms` 参数控制。若不关心应答，应改用 PUB/SUB 或 PUSH/PULL。

### 2.2 怎么用（代码）

服务端：创建服务端实例 → 用 `ssn_server_add_method` 注册方法（URL 即方法名）→ 在回调中计算结果并用 `ssn_server_response` 回复 → `ssn_server_poll` 驱动事件循环。

```c
/* 服务端：注册 RPC 方法（参考 examples/basic/02_rpc_call/server.c） */
static void add_handler(ssn_server_t *server, ssn_peer_id_t id, ssn_header_t *hdr,
                        ssn_url_ref_t *url, ssn_data_ref_t *data, void *arg)
{
    (void)url; (void)arg;

    int a = 0, b = 0;
    sscanf((const char *)data->data, "{\"a\": %d, \"b\": %d}", &a, &b);

    char response[64];
    int len = snprintf(response, sizeof(response), "%d", a + b);
    ssn_data_ref_t resp = { .data = response, .length = len };

    /* 应答必须回传请求的序列号，否则客户端无法匹配请求 */
    ssn_server_response(server, id, 0, ssn_get_seqno(hdr), &resp);
}

ssn_url_ref_t add_url = { .url = "/math/add", .url_len = 9 };
ssn_server_add_method(server, &add_url, add_handler, NULL);

/* 事件循环：轮询处理请求（或用 ssn_server_run 阻塞运行） */
while (running) {
    ssn_server_poll(server, 100);
}
```

客户端：创建客户端实例 → `ssn_client_connect`（连接超时用 `struct timespec`）→ `ssn_client_call` 发起调用并注册应答回调 → `ssn_client_poll` 驱动接收。

```c
/* 客户端：发起 RPC 调用（参考 examples/basic/02_rpc_call/client.c） */
static void rpc_reply_handler(ssn_client_t *client, ssn_header_t *hdr,
                              ssn_data_ref_t *data, void *arg)
{
    (void)client; (void)hdr;
    bool *done = (bool *)arg;

    if (data) {
        LOG_INFO("应答成功: %.*s", (int)data->length, (const char *)data->data);
    } else {
        LOG_ERROR("应答失败或超时");
    }
    *done = true;
}

ssn_url_ref_t url = { .url = "/math/add", .url_len = strlen("/math/add") };
ssn_data_ref_t data = { .data = "{\"a\": 5, \"b\": 3}", .length = 16 };
bool done = false;

/* 发起调用：timeout_ms = 5000 为应答等待超时 */
if (ssn_client_call(client, &url, &data, rpc_reply_handler, &done, 5000) < 0) {
    LOG_ERROR("RPC 调用发送失败");
}

/* 驱动事件循环，等待应答回调触发 */
while (!done) {
    ssn_client_poll(client, 100);
}
```

### 2.3 常见坑

- **超时设置分两处**：`ssn_client_call` 的 `timeout_ms` 是应答等待超时；`ssn_client_connect` 的 `timeout`（`struct timespec`）是连接超时。超时或客户端关闭时，回调的 `hdr` 与 `data` 均为 NULL；成功应答时二者均非 NULL（判断成功与否用 `hdr == NULL`）。
- **忘记驱动事件循环**：`ssn_client_call` 是异步发送，应答回调只有在 `ssn_client_poll` / `ssn_client_run` 被驱动后才会触发。只调用不轮询会「永远等不到应答」。
- **回调中不得调用 `ssn_client_close`**：回调可能在其他线程执行（客户端采用引用计数 + 锁管理），在回调中关闭客户端会导致未定义行为。正确做法是置标志位，退出回调后由主流程关闭（参见 `docs/03-设计/核心模块/线程安全设计.md`）。
- **回调参数生命周期**：回调的 `hdr` 与 `data` 指向的内存在回调返回后立即失效，如需保存数据必须自行拷贝。
- **URL 语义**：`url_len` 是字节长度、不含结尾 `'\0'`，用 `strlen` 计算（不要用 `sizeof`）；url 必须以 `/` 开头，否则调用会失败。

## 3. PUB/SUB（发布订阅）

### 3.1 何时用

- 一对多广播：一个发布者，多个订阅者；
- 异步事件通知、状态变化广播、消息推送（新闻、行情、传感器数据等）；
- 发布者与订阅者解耦：发布者不需要知道谁在订阅，订阅者也不需要知道谁在发布；
- 不关心「谁收到了、是否处理成功」——发布没有应答。

典型形态：发布端是服务端（`ssn_server_publish`），订阅端是客户端（`ssn_client_subscribe`），主题即 URL（如 `/news`、`/weather`）。订阅回调在客户端事件循环中被触发。

### 3.2 怎么用（代码）

发布端：创建服务端 → `ssn_server_start` → 用 `ssn_server_publish` 按主题发布（参考 `examples/basic/03_pubsub/publisher.c`）。

```c
/* 发布端：向主题发布消息 */
ssn_url_ref_t url = { .url = "/news", .url_len = 5 };
ssn_data_ref_t data = { .data = "Breaking news!", .length = 14 };

if (ssn_server_publish(server, &url, &data) < 0) {
    LOG_ERROR("发布到主题 /news 失败");
} else {
    LOG_INFO("已发布: %.*s", (int)data.length, (const char *)data.data);
}

/* 发布前/发布间隙仍需轮询，处理订阅者连接事件 */
ssn_server_poll(server, 100);
```

订阅端：创建客户端 → `ssn_client_connect` → `ssn_client_subscribe` 注册主题与回调 → `ssn_client_poll` 驱动接收（参考 `examples/basic/03_pubsub/subscriber.c`）。

```c
/* 订阅端：订阅主题回调 */
static void message_handler(ssn_client_t *client, ssn_url_ref_t *url,
                            ssn_data_ref_t *data, void *arg)
{
    (void)client; (void)arg;
    LOG_INFO("收到主题 %.*s 的消息: %.*s",
             (int)url->url_len, url->url,
             (int)data->length, (const char *)data->data);
}

ssn_url_ref_t news = { .url = "/news", .url_len = 5 };
if (!ssn_client_subscribe(client, &news, message_handler, NULL, 5000)) {
    LOG_ERROR("订阅主题 /news 失败");
}

while (running) {
    ssn_client_poll(client, 1000);   /* 驱动接收，触发订阅回调 */
}

/* 不再需要时退订 */
ssn_client_unsubscribe(client, &news, 5000);
```

### 3.3 常见坑

- **订阅回调规则与 REQ/REP 一致**：回调内不得调用 `ssn_client_close`；回调的 `url`、`data` 在返回后失效，需要保留的数据要拷贝。
- **`url_len` 的 strlen 语义**：`ssn_client_subscribe` 会校验 `url_len > 0` 且 url 以 `/` 开头；`url_len` 是字节长度、不含结尾 `'\0'`，应使用 `strlen`（不是 `sizeof`）。示例中的 `.url_len = 5` 对应 `/news` 的 5 个字符。
- **必须先连接成功再订阅**：订阅时若客户端未连接，`ssn_client_subscribe` 直接返回 false。
- **无持久化、无历史消息**：先发布后订阅会丢失期间的消息，订阅者只能收到订阅生效之后发布的内容。发布端如需保证「订阅者已就绪」，应像示例那样先轮询等待订阅者连接（连接回调 `ssn_server_set_connect_handler`）再开始发布。
- **发布端不能自我订阅**：发布端是服务端角色，PUB 消息发给已订阅的客户端，发布端自身的订阅/接收请走客户端角色（或使用节点层，见第 5 章）。

## 4. PUSH/PULL（管道）

### 4.1 何时用

- 任务分发：一个生产方向多个消费者推送任务，天然支持负载均衡；
- 流水线/链式处理：上游处理后把结果推给下游；
- 单向、无应答的点对点消息（「发出去即可」）。

**与 nanomsg 的差异（重要）**：nanomsg 的 PUSH/PULL 自带内置队列和负载均衡语义（消息会在对端连接后排队分发）；SSN 的 `ssn_client_message` / `ssn_server_message` 只是普通点对点消息——**没有内置队列、没有重试、没有 ACK**。任务分发所需的队列、去重、失败重试、结果回收都必须由应用层自行实现（详见 4.3 常见坑）。

典型形态：推送端是客户端（`ssn_client_message`），接收端是服务端（`ssn_server_set_message_handler` 统一接收，回调携带 `ssn_peer_id_t` 可定向回发）；服务端也可用 `ssn_server_message` 主动向指定客户端推送。

### 4.2 怎么用（代码）

推送端：发送即返回，不等待应答（参考 `examples/basic/01_hello_world/client.c`）。

```c
/* 推送端：发送任务消息 */
ssn_url_ref_t task = { .url = "/task", .url_len = 5 };
ssn_data_ref_t data = { .data = "job-1", .length = 5 };

if (ssn_client_message(client, &task, &data) < 0) {
    LOG_ERROR("任务发送失败");
}
```

接收端：注册消息处理回调（`ssn_server_msg_handler_t`），在回调中按 `id`（对端标识）区分来源，必要时用 `ssn_server_message` 定向回发。

```c
/* 接收端：处理客户端发来的消息（参考 examples/basic/01_hello_world/server.c） */
static void task_handler(ssn_server_t *server, ssn_peer_id_t id,
                         ssn_url_ref_t *url, ssn_data_ref_t *data, void *arg)
{
    (void)url; (void)arg;
    LOG_INFO("收到客户端 %u 的任务: %.*s", id,
             (int)data->length, (const char *)data->data);

    /* 处理结果可定向回发给该客户端（url2 为回发路径，与请求同 URL） */
    ssn_url_ref_t url2 = { .url = "/task", .url_len = 5 };
    ssn_data_ref_t result = { .data = "done", .length = 4 };
    ssn_server_message(server, id, &url2, &result);
}

ssn_server_set_message_handler(server, task_handler, NULL);
while (running) {
    ssn_server_poll(server, 100);
}
```

客户端若要接收服务端主动推送的消息，需注册 `ssn_client_set_on_message`（MESSAGE 类型处理回调，参考 `examples/node/02_node_comm` 中节点 B 的回复接收方式）。

### 4.3 常见坑

- **无内置队列语义**：消息不会排队、不会在消费者连上后自动补发、没有 ACK。任务分发场景必须由应用层实现任务队列（如消费者逐个领取、处理完成回报），否则消费者未就绪时消息会直接丢失。这是本模式与 nanomsg PUSH/PULL 的最大区别。
- **发送成功 ≠ 送达**：`ssn_client_message` 返回 >= 0 只表示发送调用成功，不表示对端已接收或已处理（`examples/advanced/03_timeout` 的说明：成功发送不触发发送超时）。需要确认的语义请改用 REQ/REP。
- **定向回发用 peer id**：服务端回调中的 `id`（`ssn_peer_id_t`）是对端标识，回发结果用 `ssn_server_message(server, id, ...)`；对端断开后该 id 失效，应用层需处理「回发失败」。
- **客户端收消息需注册回调**：客户端不注册 `ssn_client_set_on_message` 时，服务端发来的 MESSAGE 消息可能被忽略。

## 5. PAIR（对等）

### 5.1 何时用

- 两个进程彼此对等：双方都要能主动发起通信、既要发也要收；
- 双机/多进程握手、心跳、指令下发与结果回收；
- 希望用统一抽象（节点层）同时获得客户端与服务端能力，而不是分别管理 `ssn_client_t` 与 `ssn_server_t`；
- 一对一双向通信。若只需要一对多广播，应回到 PUB/SUB；若只是单向推送，PUSH/PULL 更轻。

节点（`ssn_node_t`）封装了客户端 + 服务端两套能力，`ssn_node_send_to_peer` 用于点对点发消息，`ssn_node_rpc_call` 用于向对等节点发起 RPC（对应 `ssn_node_add_rpc_method` 注册的方法）。

### 5.2 怎么用（代码）

创建并启动节点：服务端角色的节点建议配置监听地址与端口（`listen_port` 为 0 时退化为 Unix Socket 路径），并声明能力位（参考 `examples/node/02_node_comm/node_comm.c`、`examples/node/03_node_rpc/node_rpc.c`）。

```c
/* 节点 A：服务端角色，监听 tcp://127.0.0.1:8890 */
ssn_node_config_t config = {
    .node_type = "server",
    .node_name = "NodeA",
    .listen_address = "127.0.0.1",
    .listen_port = 8890,
    .capabilities = SSN_NODE_CAP_SERVER | SSN_NODE_CAP_CLIENT | SSN_NODE_CAP_RPC
};

ssn_node_t *node = ssn_node_create(&config);
ssn_node_start(node);

/* 注册对等 RPC 方法（回调签名同 ssn_server_rpc_handler_t，应答用 ssn_server_response） */
ssn_url_ref_t add_url = { .url = "/math/add", .url_len = 9 };
ssn_node_add_rpc_method(node, &add_url, add_handler, NULL);
```

节点 B（客户端角色）向节点 A 发消息或发起 RPC：`peer_address` 是完整传输地址。

```c
/* 节点 B：客户端角色（不配置监听地址，首次发送时创建内部客户端） */
ssn_node_config_t config_b = {
    .node_type = "client",
    .node_name = "NodeB",
    .capabilities = SSN_NODE_CAP_CLIENT | SSN_NODE_CAP_RPC
};
ssn_node_t *node_b = ssn_node_create(&config_b);
ssn_node_start(node_b);

/* 节点 B：向节点 A 发送点对点消息 */
ssn_url_ref_t url = { .url = "/message", .url_len = 8 };
ssn_data_ref_t data = { .data = "Hello from Node B!", .length = 18 };

if (!ssn_node_send_to_peer(node_b, "tcp://127.0.0.1:8890", &url, &data)) {
    LOG_ERROR("发送给对等节点失败");
}

/* 或发起 RPC：应答通过回调返回 */
if (ssn_node_rpc_call(node_b, "tcp://127.0.0.1:8890", &add_url, &data,
                      rpc_reply_handler, NULL, 5000) < 0) {
    LOG_ERROR("RPC 调用失败");
}
```

事件循环：节点的事件必须被驱动——服务端角色的节点需要周期调用 `ssn_node_poll`（示例使用后台线程轮询，`ssn_node_run` 可阻塞运行）：

```c
/* 服务端角色的节点必须轮询，否则收不到对端消息 */
while (g_running) {
    ssn_node_poll(node, 100);
}
```

### 5.3 常见坑

- **对等地址格式**：`ssn_node_send_to_peer` / `ssn_node_rpc_call` 的 `peer_address` 是完整传输地址（`tcp://host:port`、`unix:///path`、`udp://host:port`），不是节点 ID、也不是端口号本身。
- **事件循环驱动**：节点的服务端是 poll 驱动的，不调用 `ssn_node_poll` 就收不到对端消息、也无法完成连接握手。示例用后台线程持续轮询，主流程再单独轮询自身节点。
- **回调中不得重入节点 API**：回调上下文不能再次调用节点 API（`ssn_node_*`），否则可能死锁；需要在回调中回复时，直接经回调参数里的 `ssn_server_t` 调用 `ssn_server_message`（`examples/node/02_node_comm` 中节点 A 的回复即采用此方式）。
- **服务端角色节点配置**：作为服务端角色的节点建议配置 `listen_address` + `listen_port`（`listen_port` 为 0 时退化为 Unix Socket 路径），且能力位包含 `SSN_NODE_CAP_SERVER`；客户端角色的节点（无监听地址）经首次发送/订阅时创建内部客户端。
- **`ssn_node_get_client` / `ssn_node_get_server` 需持锁**：如需直接操作内部句柄，必须持有节点锁（头文件注释明确要求），一般不建议应用层直接访问。

## 6. 模式选择指南

选择通信模式前，先回答三个问题：

1. **是否需要应答？**（调用方是否关心结果）
   - 需要 → 进入第 2 步；
   - 不需要 → 进入第 3 步。
2. **双方是否对等？**
   - 对等（双方都是独立进程、都要主动发起）→ **PAIR**（`ssn_node_rpc_call` / `ssn_node_send_to_peer`）；
   - 客户端/服务端架构 → **REQ/REP**（`ssn_client_call` + `ssn_server_add_method`）。
3. **是否一对多广播？**
   - 是（一个发布者多个订阅者）→ **PUB/SUB**（`ssn_server_publish` + `ssn_client_subscribe`）；
   - 否（一对一）→
     - 单向推送、无需应答 → **PUSH/PULL**（`ssn_client_message` + `ssn_server_message`，队列由应用层管理）；
     - 双向通信、双方都要主动发起 → **PAIR**。

决策速查表：

| 场景特征 | 推荐模式 | 核心 API | 理由 |
|---|---|---|---|
| 需要应答、客户端/服务端架构 | REQ/REP | `ssn_client_call` + `ssn_server_add_method` | 请求/应答语义天然匹配 |
| 需要应答、双方对等 | PAIR（RPC） | `ssn_node_rpc_call` + `ssn_node_add_rpc_method` | 节点层统一支持双向调用 |
| 一对多通知、无需应答 | PUB/SUB | `ssn_server_publish` + `ssn_client_subscribe` | 主题订阅解耦发布者与订阅者 |
| 任务分发、流水线、无需应答 | PUSH/PULL | `ssn_client_message` + `ssn_server_message` | 单向推送；注意自建队列 |
| 双向对等、握手/心跳 | PAIR | `ssn_node_send_to_peer` | 一对一双向，节点抽象统一管理 |

补充建议：

- 不确定用哪个模式时，先看「是否要应答」：要应答的语义最明确，优先 REQ/REP；
- 订阅类场景别用 PUSH/PULL 硬做「一对一推送再自己维护订阅表」，PUB/SUB 的主题语义更清晰；
- 任务分发若需要可靠投递（不丢任务），必须在 PUSH/PULL 之上自建队列与确认机制——SSN 没有内置队列语义；
- 同一进程内可以混用多种模式：服务端同时注册 RPC 方法、发布主题、接收消息（`ssn_server_add_method` / `ssn_server_publish` / `ssn_server_set_message_handler` 互不冲突），客户端同样可以边调用 RPC 边订阅主题。
