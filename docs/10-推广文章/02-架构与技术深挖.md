# SSN 架构与技术深挖：一个 C99 IPC 框架的分层设计与踩坑实录

> 面向：对 IPC 框架内部设计感兴趣的 C/C++ 开发者。
> 本文基于 SSN v2.5.1，深度解读其分层架构、线程安全模型，以及我们在评审与修复中
> 踩过的真实坑（这些坑很多是嵌入式 C 库的共性问题）。

## 1. 分层架构：依赖方向由外向内

SSN 采用严格的分层架构，依赖方向**由外向内**，层与层之间通过接口解耦：

```
应用层
  └─ 节点抽象层    ssn_node_t（服务端 + 客户端双角色）
      └─ 客户端/服务端层  ssn_client / ssn_server / ssn_cliauto（连接管理、事件循环、路由）
          └─ 协议层    ssn_rpc / ssn_pubsub / ssn_msg（三种通信模式）
              └─ 线协议  ssn_frame（帧编解码：magic/version/type/url_len/data_len）
                  └─ 传输层  unix / tcp / udp + ssn_transport_factory
                      └─ VSI 平台抽象  ipc_socket / ipc_event / ipc_thread（内部，保留 ipc_ 前缀）
```

设计要点：

- **节点抽象层**：`ssn_node_t` 把「客户端」和「服务端」合并为一个双角色对象，一个节点
  可以同时是生产者、消费者、服务提供者——淡化传统 client/server 模式，向 DDS 的
  DomainParticipant 概念靠近（这也是本项目对标 DDS 演进的第一步）。
- **协议层模块化**：RPC / PubSub / Msg 各自独立模块，公共定义在 `ssn_protocol.h`，
  线协议统一由 `ssn_frame` 编解码。
- **VSI 层**：平台抽象（socket/event/thread/mutex），内部保留 `ipc_` 前缀，不对外——
  这是嵌入式/跨平台 C 库常见的「可移植层」模式，换平台只改这一层。

数据流（发送）：`Node → Client → Protocol → Transport`；接收方向相反。

## 2. 线程安全模型：引用计数 + 细粒度锁 + valid 标记

IPC 库最棘手的问题是**对象生命周期与多线程的交叉**。SSN 的客户端层采用了一套组合机制：

### 2.1 引用计数（ref_count）

- `ssn_client_create` 初始化引用计数为 1；
- `ssn_client_ref` / `ssn_client_unref` 在每次 API 调用期间保活对象；
- 只有**引用计数归零且 `valid == false`** 时才真正释放资源——确保正在使用对象的
  操作能安全完成，不会在调用中途被并发 close 释放。

### 2.2 细粒度锁 + 内存屏障

- 每个 client 持有一把 `client->lock`（而非全局大锁），降低锁竞争；
- 状态转换（如 `connected`）用 `ipc_memory_barrier()` 保证内存序，避免重排序问题。

### 2.3 valid 标记

- `ssn_client_close` 先置 `valid = false` → 从全局列表移除 → 减引用计数；
- `valid == false` 后，所有新操作被拒绝——「先标记失效、再清理」是避免 use-after-free
  的标准姿势。

### 2.4 回调约束（最重要的使用规则）

SSN 的回调（消息回调、RPC 应答回调）可能在**其他线程**执行，且回调期间持有锁。
因此：

> **回调内不得调用 `ssn_client_close` / `ssn_node_stop` 等销毁类操作**，也不建议
> 在回调内调用同对象的其他 API（可能死锁）。回调应只做：拷贝数据、设置标志、通知
> 其他线程，然后快速返回。

这条规则在头文件与《线程安全设计》文档中反复强调——违反它几乎是 IPC 库
「偶发崩溃」的头号来源。

## 3. 踩坑实录：评审发现的真实问题与修复

我们在 v2.4.4/v2.5.0/v2.5.1 三轮评审与修复中，发现并解决了多个真实缺陷。
这些坑很有代表性，值得分享：

### 坑 1：持锁调用用户回调 → 自锁死锁（Critical）

**问题**：`ssn_client` 的超时处理在持有 `client->lock` 时直接调用用户回调，而用户
回调内调用任何 `ssn_client_*` API（如再次 `call`、`disconnect`）都需要获取同一把
**非递归**互斥锁——同一线程重复加锁，直接死锁。

**修复**：回调一律**移出锁外**——先在锁内收集超时项（拷贝回调指针与参数），解锁后
逐个调用回调。这是 C 库中「不在持锁时执行用户代码」铁律的典型应用。

### 坑 2：事件循环空转导致客户端连接必然失败（Critical，用户旅程）

**问题**：文档化示例的服务端事件循环是 `poll(100ms) + sleep(1s)`，周期约 1.1s；
而服务端握手需要 ≥2 个 poll 周期（约 2.2s）；客户端连接握手预算却只有
固定 500ms（5×100ms）。实测按文档运行 C 示例**连接 26 次全失败**。

**修复**：
1. 客户端握手重试预算对齐用户传入的 connect 超时（默认 3s）；
2. 全部 C 示例改为**事件驱动 poll**（去掉空转 sleep）；
3. `verify_examples.sh` 增加 hello_world **运行冒烟**（此前只构建不运行，缺陷从未暴露）。

> 教训：**「构建通过」≠「可运行」**。示例/文档的代码路径必须被自动化运行验证，
> 否则用户按文档跑第一步就失败，而 CI 还全绿。

### 坑 3：半开连接永远无法感知（Critical）

**问题**：自动重连客户端（`ssn_cliauto`）从不发送保活 ping——服务端崩溃或网络中断
（无 FIN/RST 的半开连接）时，`poll` 永远超时返回、连接状态恒为「已连接」，自动重连
**永不触发**。

**修复**：实现真实 ping——按 keepalive 周期发送 `PING_ECHO`，连续
`SSN_CLIENT_AUTO_MAX_PING_LOST` 次无应答判定断开并触发重连。新增 `ssn_client_ping` API。

### 坑 4：握手超时=0 时连接被误杀（Critical）

**问题**：服务端 `conn_timeout_ms` 未设置时握手超时为 0，定时器**首个 tick**（50ms）
就销毁「连接已建立但握手包迟到」的连接——真实世界的「客户端慢启动」场景下连接偶发失败。

**修复**：`conn_timeout_ms <= 0` 回退默认握手超时（5s）。

### 坑 5：哈希表字符串键按指针比较（Important）

**问题**：哈希表的 set/get/remove 按 **key 指针值**比较，而 RPC 方法名/主题名用
调用者字符串指针作 key——内容相同但地址不同的字符串**注销静默失败**；栈 buffer
注册后 key 悬挂；重复注册同名项旧值泄漏。

**修复**：新增字符串键 API（内容哈希 + 表内复制 key），协议层改用之。

### 坑 6：协议层与主路径「两套消息类型」（Important）

**问题**：协议层 RPC 应答复用私有宏 `0x10`，而 client/server 主路径复用
`0x01 + status`——两套体系不一致，跨实现组合的 RPC 应答永远无法匹配。

**修复**：统一为 `SSN_MSG_TYPE_RPC_REQUEST`，并在请求端校验应答类型。

## 4. 工程治理：TDD + CI + 文档即代码

- **TDD 铁律**：每个修复先写回归测试（红）→ 最小修复（绿）→ 重构。新增测试
  `test_cliauto`（31 断言）、`test_hash_table`（50 断言）、server Test 11 等。
- **GitHub Actions CI**：Ubuntu 构建 + 全量 16 套件 + 19 示例 + find_package 集成，
  每次 PR 自动跑（约 5 分钟）。
- **文档即代码**：文档与代码不一致 = BUG。白皮书明确标注「愿景 vs 已实现」
  （如 QoS/节点发现仅预留能力位，不夸大成已实现），防止文档腐败。
- **问题追踪**：发现问题先提 Issue（技术债标签），择机集中修复——v2.5.1 即
  Issue #14-#19 的集中修复批次。
