# SSN 协议层模块化拆分设计方案

> `ssn_protocol_*` / `ssn_rpc_*` / `ssn_pubsub_*` / `ssn_msg_*` 调用。自 v2.6.0

> 协议层退化为「纯状态机 + 编解码」，新增 handle 原语（`ssn_rpc_handle_reply/
> handle_request`、`ssn_pubsub_handle_message`、`ssn_msg_handle_data`）作为协议层

> per-URL 订阅、方法表分发仍留在 client/server 层（收编边界见下章）。
> `ssn_*_poll` 为协议层独立嵌入/测试模式（单步：至多一次 recv + handle）；
> `ssn_protocol_run` 已标 deprecated。日常开发请使用节点层（`ssn_node_*`）或
> 客户端/服务端层（`ssn_client_*` / `ssn_server_*`）API。

## 事件循环归属（Issue #31，v2.6.0）

> 设计规格：`docs/superpowers/specs/2026-08-24-event-loop-unify-design.md`（v1.1）

**权威循环**：client/server 层（`ssn_client_poll` / `ssn_server_poll` /
`ssn_node_poll`）是唯一生产事件循环，承载多连接/握手/evtfd/定时器/引用计数
生命周期；协议层**不拥有循环**，为「纯状态机 + 编解码」。

**handle 原语（v2.6.0 新增，协议层分发入口）**：无 I/O、无锁、纯函数式，
由调用方在串行化上下文中驱动：

| 原语 | 职责 |
|---|---|
| `ssn_rpc_handle_reply` | RPC 应答帧校验 → 协议池匹配 → 触发回调并释放槽位 |
| `ssn_rpc_handle_request` | RPC 请求帧校验 → 触发 on_request（方法表由 ssn_rpc_register 维护，现状分发不经方法表，与既有 poll 行为等价） |
| `ssn_pubsub_handle_message` | PUBLISH 帧校验 → 触发 on_message |
| `ssn_msg_handle_data` | MESSAGE 帧校验 → 触发 on_message |

**收编边界（v1.1 定案）**：handle 原语不匹配上层（client/server）池——client
的 pending 池（`get_pending_snapshot` 锁内快照）、per-URL 订阅表、server 方法表
（`ssn_server_add_method` 自持）均保留在上层；协议池在生产路径为空属预期，
handle 仅做帧校验与状态机更新。client RPC 应答路径已调 `ssn_rpc_handle_reply`
做帧校验（行为等价）。

**poll 单步化**：`ssn_protocol_poll` 与子类 poll 为「至多一次 recv + 调 handle
原语」的单步模式（重构后分发收编到 handle，返回语义与重构前一致）；
`ssn_protocol_run` 标 deprecated（仅供无上层循环的嵌入/测试场景）。

**pending 双池**：client 层池为生产权威；协议层 `rpc_pending_entry_t` 池仅服务
裸 `ssn_rpc_call`，两者不可在同一连接上混用（头文件已标注禁令）。

## 背景与目标

### 当前架构分析

当前代码结构：
```
ssn_client.c    - 混杂了RPC、订阅、消息发送功能
ssn_server.c    - 混杂了RPC方法注册、响应、发布功能
ssn_protocol.c  - 基础协议解析
```

**存在的问题**：
1. 协议逻辑与传输逻辑耦合在一起
2. 客户端/服务端代码臃肿，难以维护
3. RPC、发布订阅、消息三种协议混在一起
4. 无法灵活替换或扩展协议实现
5. 会话层（node）与协议层边界不清晰

### 目标

拆分出独立的协议层模块：
1. **RPC协议层** - 请求/应答模式
2. **发布订阅协议层** - 发布/订阅模式
3. **消息协议层** - 发送/接收模式

## 目标架构设计

### 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│                    应用程序层 (Application)                    │
├─────────────────────────────────────────────────────────────┤
│                    节点抽象层 (Node Abstraction)              │
├─────────────────────────────────────────────────────────────┤
│                    协议层 (Protocol Layer)                    │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐        │
│  │  RPC协议   │  │ PubSub协议  │  │  MSG协议    │        │
│  │  (req/rep) │  │  (pub/sub)  │  │  (send/recv)│        │
│  └─────────────┘  └─────────────┘  └─────────────┘        │
├─────────────────────────────────────────────────────────────┤
│                    传输层 (Transport Layer)                  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐        │
│  │    TCP     │  │    UDP     │  │    Unix    │        │
│  └─────────────┘  └─────────────┘  └─────────────┘        │
└─────────────────────────────────────────────────────────────┘
```

### 模块划分

```
src/
  protocol/
    ssn_protocol.h           # 公共协议定义
    ssn_protocol.c           # 协议基础实现
    
  protocol/
    rpc/
      ssn_rpc.h              # RPC协议接口
      ssn_rpc.c              # RPC协议实现 (req/rep)
    
    pubsub/
      ssn_pubsub.h           # 发布订阅协议接口
      ssn_pubsub.c           # 发布订阅协议实现 (pub/sub)
    
    msg/
      ssn_msg.h              # 消息协议接口
      ssn_msg.c              # 消息协议实现 (send/recv)
```

## 协议层详细设计

### 1. 公共协议基础

#### 1.1 协议类型枚举

```c
/**
 * @brief 协议类型枚举
 */
typedef enum {
    SSN_PROTOCOL_RPC = 0,      // RPC请求-应答协议
    SSN_PROTOCOL_PUBSUB,       // 发布-订阅协议
    SSN_PROTOCOL_MSG           // 点对点消息协议
} ssn_protocol_type_t;
```

#### 1.2 协议上下文基类

```c
/**
 * @brief 协议上下文基类
 */
typedef struct ssn_protocol_ctx {
    ssn_protocol_type_t type;      // 协议类型
    ssn_role_t role;               // 协议角色
    ssn_transport_t *transport;    // 底层传输
    void *user_data;               // 用户数据
    void (*destroy)(struct ssn_protocol_ctx *ctx);  // 销毁函数
} ssn_protocol_ctx_t;
```

### 2. RPC协议层（req/rep）

#### 2.1 RPC上下文结构

```c
/**
 * @brief RPC协议上下文 - 请求端（客户端）
 */
typedef struct ssn_rpc_req {
    ssn_protocol_ctx_t base;           // 基类
    
    // 待处理请求管理
    rpc_pending_entry_t *pending_pool; // 待处理请求池
    void *pending_lock;                // 待处理请求锁
    
    // 回调函数
    ssn_rpc_reply_handler_t on_reply; // 收到应答回调
    uint16_t next_seqno;              // 下一个序列号
} ssn_rpc_req_t;

/**
 * @brief RPC协议上下文 - 应答端（服务端）
 */
typedef struct ssn_rpc_rep {
    ssn_protocol_ctx_t base;           // 基类
    
    // RPC方法表
    void *method_table;                // RPC方法注册表
    size_t method_count;               // 方法数量
    
    // 回调函数
    ssn_rpc_handler_t on_request;      // 收到请求回调
} ssn_rpc_rep_t;
```

```c
 * @param ctx 协议上下文
 */
SSN_API void ssn_protocol_run(ssn_protocol_ctx_t *ctx);

/**
 * @brief 检查协议是否已连接
 *
 * @param ctx 协议上下文
 * @return 已连接返回true，否则返回false
 */
SSN_API bool ssn_protocol_is_connected(ssn_protocol_ctx_t *ctx);
```

### 示例1：RPC请求-应答


## 注意事项

1. **线程安全**：协议层本身不是线程安全的，需要调用方保证同步
2. **内存管理**：协议上下文创建后需要调用对应destroy函数释放
3. **传输层依赖**：协议层依赖于底层传输层，需要先创建传输层
4. **回调函数**：回调函数在收到数据时被调用，需要快速返回避免阻塞

## 总结

通过将协议层拆分为独立的RPC、发布订阅和消息三个模块：

1. **职责清晰**：每个协议模块职责单一，易于维护
2. **可扩展性强**：可以独立扩展或替换某个协议实现
3. **代码复用**：公共协议基础代码被复用
4. **易于测试**：每个模块可以独立进行单元测试
5. **灵活组合**：用户可以选择使用哪些协议，传输层也可以灵活选择

这套设计实现了协议层与传输层的完全解耦，让用户可以灵活组合使用。
